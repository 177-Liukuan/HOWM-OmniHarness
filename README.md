# HOWM-OmniHarness

把 OmniHarness 的「先规划、执行观察、核对结果、按具体问题补证据」迁到 HOWM 30 选 1。原生 Codex 调用本地 Qwen3.5-9B；Python 负责执行、检查和提交。首版先跑真实题，不采用 TDD。

## 独立代码仓库

本方法单独使用 Git 管理，远端为 [177-Liukuan/HOWM-OmniHarness](https://github.com/177-Liukuan/HOWM-OmniHarness)（私有仓库）。它是当前目录自己的仓库，不是父项目的子模块。

仓库包含代码、提示词、配置、上游来源说明，以及[最新开发验证结果](results/2026-10-04-focused-review/README.md)。数据集、模型权重、原生会话与完整运行输出继续保留在HOWM-LAB工作区，不纳入版本控制。归档的四题预测不是全量官方提交。

现有启动脚本仍依赖本机HOWM-LAB目录、已有Docker镜像和常驻模型服务；独立克隆仓库不等于已具备运行环境。迁移机器时需按下方说明准备资源并核对脚本中的路径。

## 一题怎样跑

默认只调用三个角色，共用本题同一原生 Codex 线程：

1. **Planning**：根据首尾和30候选基础图生成观察重点、检查标准与策略；固定三步的依赖关系和30项编号绑定由Python生成。采样与裁剪始终可申请，工具可用性由Python固定，不让模型生成权限名单；调用仍须通过疑点和预算检查。
2. **Observation**：按计划一次输出首尾观察、30项逐项观察、主要候选排序与理由，以及仍不能排除的候选。
3. **Review**：Python先为最有竞争力的候选生成清晰视频图板；Review收到首尾图、候选图板和全部30项简短记录，检查每步标准并决策。首次Review默认不重发三张总览图。

Final Decision 由 Python 检查后直接写入，不再调用模型。Review 只有同时给出具体疑点、可能改变排序、合法且未重复的取证请求，才能进入 Slow Path。补帧或裁剪后仅增加一次 Review。充分就结束，不要求耗完轮数。

原始 instruction 原文输入；题号保留 `094` 这样的字符串；答案是原候选整数1–30。每题只使用自己的 JSON 引用媒体，不读取未引用的 state.mp4 或教师答案。模型没有 shell、写文件、网页或子代理工具。图片通过原生 `--image` 输入，日志验证同题线程和实际编码图片回执；回执不代表模型一定理解正确。

## 运行

服务为 `howm-omniharness-qwen9b`，runner 与其共享网络。服务常驻，不在实验结束时释放显存。使用已有 Docker 镜像，不需要污染宿主机 Python 环境。

```bash
cd /storage1/HOWM-LAB-Project/methods/howm-omniharness
./launch.sh howm-omni-my-smoke 001,003,026,036,049,076,094,4884
# 同一命令续跑：已成功提交题跳过，继续使用这个实验的源码快照。
# 修改方法后必须换新的实验名；不修改旧实验 source。
./launch.sh howm-omni-repeat 001,003,026,036,049,076,094,4884
# 两次独立小样本通过、耗时可接受后，再由使用者启动全量：
./launch.sh howm-omni-full --all
```

输出在 `outputs/<实验名>/`：

- `source/`：本次完整源码、提示词、配置快照。
- `submission.jsonl`：每完成一题就加锁追加、flush/fsync，无答案分片和合并步骤。
- `questions/<qid>/`：计划、30项观察、每次 Review、预算与错误；`turns/` 保存每次命令、提示、原生事件和图像回执。
- `evidence/<qid>/`：四张基础图、可选补证据、原始媒体哈希和实际帧时间。
- `summary.json`：完成率、Fast/Slow、调用/取证/时间均值和分位数、5000题分配 GPU·小时估算。公开数据无 GT，accuracy 为 null。
- `run-config.json`、`preflight.json`：配置哈希、实际模型/上下文、环境。

失败不填默认答案，不重复追加。已有完整答案不会被覆盖。损坏的提交末行须先用 `vendor/submission_io.py repair-tail` 明确修复（会保留被移除字节），不能静默丢弃中间错误。

## 预算与第一版边界

默认软预算：8 turns、2 attempts、2批主动补证据、300秒；请求额度为实际自动图板数加4个主动请求，最多8个。普通题目标是3 turns；自动采样计入requests和单题时间，不能将它记成零成本。绝对上限：96 turns、9 attempts、8批、32请求、2400秒。合法且有实际更新的新证据请求才可小额扩展，最多6次。收尾最多120秒且仍在绝对上限内。超时只终止本题进程，不停模型服务。

计数在调用前落盘，恢复不重置；未确定完成的预留按最坏预留时间计入。首版对执行中断采取保守停止，记录技术失败，**不自动重开新线程或恢复到旧决定**。已写答案可安全跳过，干净阶段检查点可续跑。上下文压缩后恢复、隔离修复线程与细粒度依赖图后置；检测到自动压缩即拒绝提交，不冒充支持。补证据期间旧决定失效，必须完成最新 Review。

基础媒体固定3帧（5%、50%、95%）；抽样不能保证看见瞬时动作。补帧记录实际 PTS；裁剪从原状态图/原分辨率视频帧取图。模型声称语义正确不等于正确答案。当前方法库初始为空（build），不默认把旧教师示例混入输入。

## 聚焦候选的 Review

全量观察仍逐项覆盖原编号1–30。`comparison.ranking` 按竞争力列出2–6项及理由，首项是初选；`not_ruled_out`保留尚不能排除的候选。Python只是按模型顺序派生`best_candidate`与`main_competitors`，不打分、不替换答案、不丢掉30项记录。Review也使用一个有序列表输出判断，再由Python派生提交字段，避免模型把最佳项重复写成自己的竞争项。

默认选初选及最强竞争项，合计最多4项。每项从原视频的5%–95%区间均匀抽6帧，拼成两列三行、1024×960图板；单帧显示区域512×288，标注候选编号及实际解码时间戳（相对视频起点）。文件名前缀`option_NN`与图板标题`Option N`保持一致，引用校验会拦截候选与图板串号。它比30候选总览中的320×180缩略帧更适合看动作方向，又无需为默认图板触发原生CLI的2048像素整体缩小。源文件SHA、请求/实际时间、图板SHA和执行时间均记录在证据JSON里；按请求、布局、原视频与图板哈希验证缓存。

首次Review只重发首尾图和这2–4张图板，同时收到完整30项观察。之前的总览仍在同题原生Codex会话历史里；“不重发”不等于删除历史。暂未生成图板的候选未被排除，Review可以改选1–30中的任何选项，也可以用现有`sample_video`查看新候选。具体时序疑点用局部时段补帧，细节疑点用`crop_evidence`从原图或原视频帧裁剪；新增证据后必须再次Review，旧决定在此期间失效。

自动图板生成不调用模型，也不记为Slow Path，但每张图板计1个requests，并受同一软/硬时间预算约束。记录分别提供`automatic_requests`、`requested_requests`、自动/主动媒体耗时和新增解码帧数；硬上限32个请求包含自动采样。`summary.json`保留Fast/Slow及调用/时间分位数。基础30视频的90帧预处理也计入总耗时，新增解码帧数不包含这固定90帧。字段`decoded_frames`统计工具实际返回的抽样帧数，不是ffmpeg内部扫描解码的所有帧；真实媒体执行成本以耗时为准。

默认6帧不能保证捕获瞬时动作；高帧数长图可能被CLI缩小，因此细节比较应优先分段采样或原图裁剪。图像回执、引用和覆盖检查只证明实际输入与协议正确，不证明模型理解正确。教师答案只在推理完成后的独立评分中读取。

本次修改前后实验见[实测报告](results/2026-10-04-focused-review/报告.md)。固定4道开发题的完成数从3/4变为4/4，平均角色调用3.50→3.25，平均单题耗时91.9→175.5秒（均含失败题；共享服务，不是独立吞吐基准）。最终版3题走Fast Path、1题走Slow Path，无格式重试；教师预测一致1/4，不是官方准确率，也不足以证明效果提升。

独立094题诊断还验证了：在原会话和累计预算内查看初选名单外候选、裁剪原始状态图、使旧结果失效后再次Review；新增2次取证、1次模型调用，不写提交、不混入上述指标。

旧实验保持原样，新测试从独立目录开始，常驻模型服务未重启。按用户要求，本次验证与报告完成后停止，不启动后续265题实验，也不继续扩展优化；原265题批量练习保持暂停。

## 离线自主练习和方法库

`practice.py` 实现一个有边界的首版循环：在 C01–C10 中选能力和真实练习题 → 使用同一个在线控制器独立解题 → 程序侧与冻结教师预测比较 → 提炼待审核方法卡/失败提醒。教师答案不进入 Planner、Observer、Review 或蒸馏提示；蒸馏只收到学生轨迹和是否匹配。暂时只练完整30选1题，不伪造 micro-QA 的标签，不把265题当未见过的验证集。

在独立离线 runner 中使用（`/reference/submission.jsonl` 只挂在离线 runner）：

```bash
python /method/practice.py --data /data --output /work \
  --reference /reference/submission.jsonl --ids 001,094,4884 --rounds 1
```

`episode-*/candidate-policy.json` 均为 `pending_human_review`。人工检查适用条件、步骤、证据、题号/答案记忆泄漏和伪标签风险后，才使用 `policy.py --reviewer ... --review-note ... --output 新bundle.json` 发布。这个命令记录审核，不代替审核本身。将审核冻结的 bundle 放入新版本的 `config/policies.json`，新开实验；正在运行的实验不改变方法库。

`evaluate.py` 在宿主机离线比较已完成预测，不给推理程序挂教师答案：

```bash
python evaluate.py --output /绝对路径/teacher-match.json teacher /绝对路径/run /绝对路径/教师submission.jsonl
python evaluate.py --output /绝对路径/repeat.json repeat /绝对路径/run-a /绝对路径/run-b
```

报告完成率、已完成题教师一致率、计划题单整体匹配率；不称为官方准确率。独立重复要求两次 run-config/source 一致、各自从空结果开始。

## 快速实现中后置的内容

首版只执行三个紧凑计划步骤（首尾观察、候选观察、比较），重复操作应合并关注点，避免接受无法完整执行的计划。复杂压缩与恢复、隔离修复会话、自动生成 micro-QA、完整消融、并发吞吐优化尚未交付。按状态哈希分组的内部验证集和批量练习入口已加入，见下节。首版采用保守的整份观察/比较失效与最新 Review 重验，不实现细粒度依赖恢复。媒体调用失败直接记录技术失败，不伪装成语义看不清；尚未加自动工具重试。旧 practice.py 只支持新目录；新 campaign/practice_batch.py 可以跳过已落盘的完整练习，并保留中断题的预算和失败记录，不静默重开中断的模型调用。

实现后使用真实 `094` 媒体做 `validate_runtime.py` 检查；这验证工具和可靠性边界，不证明模型准确率。现场实验报告位于 `evaluations/howm-omniharness-development-20261004/`。


## 已实测的首版结果（2026-10-04）

固定版本在001、094两题上从空目录独立运行两次：四次单题运行全部完成，答案2/2一致，每题3次角色调用、零协议重试。单题约153–181秒。受控真实视频补证据测试通过（原线程新增一次Review）；另完成一次离线练习，产生待人工审核的方法卡。

这只有2个唯一开发题，尚非全量验收或准确率证明；按当前单worker样本吞吐粗估5000题约9.8天、约469 GPU·小时，需扩大样本和测并发后再作全量预算。完整记录、已知边界及旧版失败修复见 [首版实现与验证报告](../../evaluations/howm-omniharness-development-20261004/report.md)。没有运行5000题或提交官方。


## 265题批量练习与内部验证（新增入口）

本轮总入口为 `campaign/driver.py`。它在宿主机调度已有 Docker 服务，依次运行：

1. `campaign/prepare.py` 固定原始265题，按首尾图片哈希成组拆分201题练习、64题内部验证；先划分，后读取教师分析。两组无相同首尾状态组合，但有共享视频，不能当完全独立测试集。
2. `campaign/practice_batch.py` 每批由模型从能力/题目内容索引选择8题。先监督跑8题，再32题试跑，通过技术检查后继续201题。模型选出的自由文字目标只供离线记录；解题器仅获得能力名称及原题媒体，避免教师描述泄漏。
3. 每题先保存 `episodes/<qid>/first-pass.json`；与教师不一致时最多开启一次反馈复核。只告诉它“不一致”，不提供教师选项；沿用原线程和剩余预算。首次答案、复核答案、技术失败分开统计，重复启动不重复计分。
4. `campaign/distill.py` 每项能力结合至少3个不同首尾状态案例及额外反例，实际查看练习证据图，产生通用候选卡。卡片正文不能写题号/选项答案；教师观察是待核对解释，不是事实保证。正式方法库不自动更新。
5. 在64题上分别以空库和候选库独立推理。在线 runner 不挂载教师答案或分析；宿主机 `campaign/compare.py` 事后评分，记录教师一致率、变好/变差题、方法选用次数及耗时。
6. 生成 `review/REVIEW.md` 后停在人工审核点。经实际审核冻结方法库后，才能另开全265题在线实验；练习和验证结果不能冒充该次正式在线结果。

本轮记录目录：`evaluations/howm-omniharness-265-20261004T055659Z/`；练习输出：`outputs/howm-omniharness-265-practice-20261004T055659Z/`。进度见前者 `campaign-status.json`、`logs/`，以及后者 `summary.json`。正式方法库仍以 `config/policies.json` 的实际内容为准。

新的在线 `run.py` 支持 `--manifest /manifest.json --policy-file /policy.json`，每题直接加锁追加同一个 `submission.jsonl`。**原始265题必须用固定 manifest；`--all` 指全部5000题。** A/B实验只改变 policy bundle，使用相同源码、模型和题目顺序。基础页来源由Python按题号/候选编号绑定；原生图片回执证明实际输入，不能证明模型已正确理解。

完整模型调用、媒体、预算和首次/复核轨迹均保留。首版仍对调用中途崩溃保守停止，不恢复到失效决定，不清空预算。批量控制器遇到连续累计两题技术失败会暂停等待检查，不能靠填默认答案完成题单。
